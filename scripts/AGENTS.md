# DOX — Scripts

## Purpose

Owns the repository's gate and maintenance scripts: preflight orchestration, PR scope and review evidence, DOX claim verification, staleness detection, evidence-integrity and checker pinning, plus release/build helpers. These scripts are the checked authority for repository rules; prose in `AGENTS.md` describes them but never replaces them.

## Ownership

- `preflight.mjs` — local/CI gate runner (`pnpm preflight`); the pre-push hook's entry point.
- `check-pr-scope.mjs`, `check-review-evidence.mjs` — PR scope declaration and review-record verdicts.
- `check-dox-claims.mjs`, `check-staleness.mjs` — AGENTS.md contract verification and reference drift.
- `check-dox-scope.mjs` — read-only Codex-target instruction chain and byte-budget preflight.
- `audit-dox-overlap.mjs` — advisory comparison of long, directly inherited contract bullets; reports exact and high-similarity overlap candidates without changing DOX.
- `plan-codex-context.mjs` — read-only Codex source-retrieval shortlist using DOX scope and a verified current GitNexus checkout; stale/unknown graph results never authorize edits.
- `audit-codex-tokens.mjs` — read-only measurement of cumulative Codex session token counters, tool-call counts and compactions, with explicit separation from RTK and TokenEconomizer estimates.
- `compare-codex-context.mjs` — offline, read-only paired baseline-versus-guided session comparison; rejects mismatched models or missing usage and does not claim causal savings.
- `check-evidence-integrity.mjs` — evidence ordering, generator reproducibility, checker/manifest reflexivity.
- `check-dead-modules.mjs`, `check-boundaries.sh`, `check-pr-conventions.mjs`, `check-package-manager.sh`, `check-supply-chain.sh` — dead-module, architecture, PR-title, package-manager, and supply-chain gates.
- `scripts/srap-accept/AGENTS.md` — SRAP acceptance fixture; carries no product logic and is never imported by `src/**`.

## Local Contracts

- **Preflight is fail-closed.** `pnpm preflight` (`scripts/preflight.mjs`) reports `PASS`, `FAIL`, `SKIP`, or `UNKNOWN` (`not_checked`). Only `PASS` and explicit `SKIP` are clean: `not_checked` means a required check could not run, prints its reason, and exits 1. The pre-push hook (`.githooks/pre-push`, installed with `pnpm hooks:install`) runs it for any non-empty branch diff (preflight itself skips type/tests for a docs-only diff); CI remains the authority. A requested `--base` that does not resolve is an invocation error, never a silent fallback to an uncommitted-only diff; `resolveChangeSet` refuses the same way when no base resolves AND `HEAD` has ancestors, recording `changed files` as `not_checked` rather than passing over a fragment of the branch. Only a genuine root-only repository may treat its uncommitted files as the whole change set. Affected-test selection is a local heuristic (mirrored path, basename, static/dynamic import), not GitNexus `detect_changes`; unselected changes are counted and reported, and `--full` is the authoritative run. The hook diffs a new branch against its merge base with `origin/main` and fails on an existing remote SHA it cannot resolve; `tests/scripts/pre-push.test.mjs` pins those base choices.
- **Checker scripts are sha256-pinned in CI.** The `Checker script pins (sha256)` step in `.github/workflows/ci.yml` pins `scripts/check-evidence-integrity.mjs`, `scripts/check-dox-claims.mjs`, `scripts/check-staleness.mjs`, `scripts/check-pr-scope.mjs`, and `scripts/check-review-evidence.mjs`, so weakening a gate is a visible workflow edit rather than a one-line diff. The honest limit: an author can change a script and its pin together, so this is a cost and a review signal, not cryptographic independence. Editing a pinned checker without updating the pin fails the build.
- **PR scope is a checked verdict.** `scripts/check-pr-scope.mjs` requires base `main` (an `origin/main` diff ref is read as `main`) and a `Scope:` label whose value covers every touched top-level area. A diff spanning more than three areas must also carry a `Broad-scope:` line stating why it is one change; a declaration alone is not a reason, because it says where the diff goes, not why it belongs together. The cap is a prompt for a stated decision, not a prohibition — recent merged work legitimately spans 5 and 11 areas. Checked-in hooks (`.githooks/**`) count as `scripts`. Parse a declaration by label and colon, never by the bare word `scope`: a hyphen is a word boundary, so keyword matching read `check-pr-scope.mjs` as `Scope: scripts/check-pr-scope.mjs`. **The area list is derived from the tree, not remembered.** `tests/scripts/check-pr-scope.test.mjs` reads `git ls-files` and fails when any tracked path classifies `unclassified`, when an `AREAS` entry matches no tracked path, or when a root file is neither in `SHARED_PATHS` nor assigned one — so a new top-level directory fails a test with its own name instead of failing an author's PR. The four root `src/*.ts` modules are the `src/entry` area, never a blanket `src`. Root files are enumerated individually: exempting `/^[^/]+$/` would remove new root content from review scope. `unquoteGitPath` decodes git's C-quoted non-ASCII names (`"docs/…/if\\303\\241-…md"`), which previously made that file `unclassified`. **Retiring an area is explicit.** When the last file of a top-level area is deleted, the area moves from `AREAS` to `RETIRED_AREAS` rather than being dropped: a retired name still classifies its own paths (so the deleting PR can declare it instead of being told the path is `unclassified`), and must own no tracked path — a test enforces both directions, so re-adding content there fails until the area is promoted back into `AREAS`.
- **DOX claim verification.** Added source paths and identifiers must resolve to branch content. `pnpm check:dox` audits added contracts (list bullets **and** index-table rows), whole-file bullet corruption, and model-facing tool vocabulary; generated GitNexus guidance is exempt. Table rows count because DOX Ownership and Child DOX Index sections are tables — before that, a table-only edit reported zero files audited. Its diff scope does not certify pre-existing claims. Empty default-branch or documentation-free comparisons may pass; invalid refs or differing refs with no changed files are invocation errors. **Identifier resolution must span every depth.** `git grep` accepts a bare `**` pathspec but a leading `**` segment then requires at least one directory, so `src/**/*.ts` silently skipped the four top-level `src/*.ts` modules and `scripts/**/*.mjs` skipped every top-level script — correct contracts naming symbols from those files were reported `no code` regardless of source. `SOURCE_PATHSPECS` uses `:(glob)` magic, the form that covers zero or more directories; `tests/scripts/check-dox-claims.test.mjs` pins both directions against a throwaway repo (a top-level symbol resolves; an undefined symbol still fails), because a gate that only ever passes is not a gate.
- **Staleness sentinel.** A reference that no longer describes the tree reads as coverage that does not exist. `pnpm check:staleness` (`scripts/check-staleness.mjs`) runs in the git-only CI lane and fails on a `$schema` that does not resolve, a root-relative path named in `AGENTS.md`/`README.md`/`CONTEXT.md`/`docs/security/**` that does not resolve, a policy document that has drifted from the schema it declares, or an exception entry that can never match an advisory. It deliberately does not check exception expiry or advisory matching — those are policy verdicts owned by `checkExceptionsPolicy` and `runExceptionsCheck`, and a second implementation would drift from the first. `tests/scripts/check-staleness.test.ts` pins each verdict against a fixture root; a check that cannot fail would report OK over the drift it exists to catch.
- **Evidence gates report only what they performed.** `scripts/check-evidence-integrity.mjs` requires the manifest to postdate every artifact it indexes — an artifact and its index entry in one commit is a finding — and verifies checker/manifest reflexivity. Reflexivity judges EDIT history: a commit that changes the checker and an already-existing manifest (or artifact) it judges is a finding. The question is asked of EVERY commit whose checker blob differs from its FIRST parent, not only the newest and not only commits that *authored* a rule — selecting the latest rule-authoring commit let a violation at commit N hide behind a harmless checker-only commit N+1, and asking only authors missed a merge that lands a side branch's rule and its data together. Each such commit is read against its own `diff-tree -m` record, never `git log -1 -- <path>`: default history simplification reports a side commit for a merge that carries a path, so a merge landing a first manifest while rewriting the rule looked like data older than the rule. Data counts as changed at a merge only against the FIRST parent — the parent the merge was performed on, not necessarily the trunk: resolving in favour of it is not a changed data set, landing a side branch's version (or authoring a third) is. Measuring the RULE against the first parent likewise keeps an honest resolution out: a merge that keeps trunk's checker byte for byte changed no rule, and a checker record against the second parent is the version the merge rejected. A commit authors a path when the path differs from EVERY parent (one `-m` record per parent) and a blob exists there; landing a version unchanged from one parent authors nothing, and deleting a path authors nothing. A commit that carries data authored elsewhere is excused when the rule version it enforces was authored at or before that data's author — the ordinary split branch, and a merge landing such a pair launders nothing; the excuse does not apply when the rule landed on a branch the data never had. Keeping the FIRST parent's data does not by itself excuse the rule in the same commit: that rule must have been authored by the commit, or its author commit must itself carry the identical data blob — had this rule version seen this data version? Branch lineage is not the test, so a rule authored on a side branch that already carried those exact bytes is honest, while a merge that keeps one parent's manifest and adopts a rule whose author never carried that blob is a finding. "Who authored the rule" is asked of the VERSION, not the path: the authoring commit must itself carry the identical checker blob, because topological order can list a three-parent merge's side branch that rewrote the rule while inheriting the data ahead of the branch whose rule the merge lands, and accepting it would compare the wrong commit's data and excuse the adoption. A carried version whose own author commit changed the rule too is a genuine joint bootstrap only if the path was new to every parent of the commit that lands it. A bootstrap requires four things: the path's entire history is that one commit; the path was new to EVERY parent, so a merge cannot replace a parent's already-judged manifest with a side branch's genuine "first" version; that commit created the path there rather than relocating content into it — a rename or copy destination also has exactly one commit in its history, so the sole-commit count alone cannot tell creation from a move; and the content did not already exist anywhere in the commit's reachable ancestry. The fourth condition exists because rename/copy detection only reads a PARENT TREE: parking byte-identical content at a scratch path and deleting it in an earlier commit leaves `A` + `M` records and a one-commit path history, and only blob identity over ancestry sees it. A shallow clone cannot answer that question, so it fails closed rather than granting the exemption on a truncated search. Deleting and re-adding a path is not a bootstrap — the delete stays in its history. The honest limit: content that was never committed anywhere in reachable history is indistinguishable from a genuine first manifest, which is the point of the carve-out; this narrows the cheap edit, it does not make the order rule unbypassable. `--recompute` re-runs only generators that declare themselves reproducible; a generator with `recompute: false` is reported NOT CHECKED, never counted as a pass. `--max-recompute-skipped <n>` bounds that declared-non-reproducible set shrink-only: declaring one more generator exempt from regeneration fails until the pin is raised deliberately, and a drop below the pin must be matched by lowering it. `--allow-declared-skips` does not widen the gate: it converts a `not_checked` verdict to `pass_with_declared_skips` only when every unchecked reason is a declared skip AND the run recorded zero blocking findings, so a real finding can never be acknowledged away by passing the flag. `--max-accepted` is the same ratchet for accepted historic order defects.

- **Codex DOX scope preflight is advisory about reads, definitive about on-disk chains.** `pnpm check:dox:scope` enumerates scoped `AGENTS.md` chains and verifies their cumulative byte sizes against `project_doc_max_bytes` in the global Codex config (default 32,768). `node scripts/check-dox-scope.mjs --path src/coordination/kernel/file.ts` shows the exact required chain for a target, including prospective files. `--config` and `--budget` support explicit overrides; `--json` returns machine-readable findings. The script cannot prove the model consumed the documents; never represent a clean scope result as proof of an actual read. `tests/scripts/check-dox-scope.test.mjs` covers chains, budget rejection, and escaping paths. It is a separate preflight, not a second DOX contract authority.

- **Instruction overlap audit is advisory.** `pnpm audit:dox:overlap` compares long contract bullets only within actual ancestor chains, reporting byte-identical statements separately from token-similarity candidates. Sibling scopes never count as inherited duplication; the threshold is a heuristic and can miss paraphrases. Neither exact nor approximate overlap permits automatic removal: retain security, authority, and scope-specific wording until manual ownership/equivalence review. `tests/scripts/audit-dox-overlap.test.mjs` pins exact/approximate detection and sibling isolation. This complements `check-dox-scope.mjs` without duplicating DOX claim validation.

- **GitNexus-assisted Codex retrieval is advisory, never a safety verdict.** `pnpm plan:codex:context -- --query "concept" --path src/example.ts` calls the DOX scope checker to enumerate mandatory ancestor instructions and checks GitNexus status for current repository, branch and commit before accepting source candidates. A stale, absent or unparseable graph yields no candidates and an explicit unknown finding, never a zero-impact result; only exact workspace-contained existing source paths are short-listed, with a configurable `--max-files` ceiling. For single-identifier queries, bounded local `git grep` runs only after freshness validation and ranks exact declarations, dedicated tests, other tests, then source references ahead of graph candidates. The source-reference category does not prove a direct caller; a file absent from either source/graph search remains UNKNOWN. The operator/agent must still read the real DOX and source files, use GitNexus impact for actual edits, and follow all existing security and review gates. It does not modify Codex internals or automatically load files. `tests/scripts/plan-codex-context.test.mjs` tests stale/current states, bounds, and traversal rejection.

- **Codex efficiency measurements do not imply causal savings.** `pnpm audit:codex:tokens` reads the newest local Codex JSONL log; `node scripts/audit-codex-tokens.mjs --file <path> --json` allows explicit audited input. It reads the last cumulative `thread_token_usage` (or `usage`) from `token_usage_record`, never sums snapshots, and reports tool calls, compactions and invalid lines. RTK estimates (`rtk gain -p --format json`) and TokenEconomizer status (`~/.tokeneconomizer/bin/te --host codex status`) are separate, potentially overlapping observations, not additions to or deductions from Codex token counters. Before claiming planner savings, compare matched tasks under the same model, prompt, tools and plugin settings with and without the planner, verifying correctness and missed dependencies; recorded session snapshots alone establish no performance advantage. `tests/scripts/audit-codex-tokens.test.mjs` pins cumulative accounting and attribution caveats.

- **Paired context experiments require matched evidence.** `pnpm compare:codex:context -- --baseline <jsonl> --guided <jsonl>` compares two distinct recorded sessions using `audit-codex-tokens.mjs`. It rejects missing counters and model mismatches, reports cached tokens separately, and explicitly disclaims causal savings without matched tasks, answer accuracy, tool parity, and RTK/TokenEconomizer parity. A stale/degraded GitNexus index blocks the guided retrieval experiment; never infer coverage from an empty graph. `tests/scripts/compare-codex-context.test.mjs` pins comparison and rejection behavior.

## Work Guidance

- Add a gate by adding a script and wiring it into `preflight.mjs` or CI; a gate that no lane runs is not a gate.
- Change a verdict's meaning together with its test, and update the sha256 pin in CI when a pinned checker changes.
- Keep scripts offline and deterministic; a checker that needs network or a live model cannot be a CI authority.
