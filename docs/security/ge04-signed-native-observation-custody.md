# GE-04 — Root-custodied signed fixture observation (Ed25519)

**Security decision: HOLD. No production authority or trusted effect receipt.**

This checkpoint introduces `experiments/ge04/signed-native-observation-fixture.py` to separate **public signature verification** from possession of the experimental signing key. The root-only test provisioner generates a fresh ephemeral Ed25519 private key in a root-owned 0700 directory (key mode 0600) and publishes a verification key and a signed, create-once fixture record in a root-owned 0755 directory (files 0644). A separately executed untrusted coordinator under UID/GID 65534 can verify the signature using only the public key and the **test provisioner's explicitly pinned** SHA-256 verification-key digest; it must be unable to read or change the private key or overwrite the already signed record.

The signing record binds exact fixed test attempt, approval and lease identifiers, policy revision, fixture observation SHA-256, fixture effect-byte SHA-256, signer-key digest, and the fixed status `NATIVE_FIXTURE_OBSERVED_UNVERIFIED`, with an Ed25519 signature over domain-separated canonical JSON. File creation is `O_EXCL|O_NOFOLLOW` and both record and containing directory are fsynced. The verifier rejects malformed or duplicate JSON fields, mismatched signatures/key pins, content hashes, and status claims. The root-only test deliberately rejects signing with an unsettled inFlight attempt and denies signing twice. Cross-UID tests exercise signature validation, private-key read/write denial, public-file overwrite denial, digest mismatches, forgery and replay.

**What this does not establish:** The root provisioner controls the private signing key, public-key trust pin, and input observation bytes. The signing function accepts caller-supplied bytes; a root-equivalent attacker can fabricate a convincing record without any native kernel effect. Even for an honest signer, the signed record is not atomically linked to `openat2`, `fsync`, a supervisor-owned authoritative approval store or a trusted terminal execution journal. Receipt verification proves only that a particular **test key** signed particular input, NOT who performed an OS mutation, its durability, or its authorization. A lost receipt or an unsettled approval remains `UNCERTAIN_NO_REPLAY` under the existing protected fixture. The new signed fixture is deliberately **not registered as a success oracle or invoked by a production mutation path**.

The next release blockers are a signer/receipt generator inside the separately provisioned protected supervisor, a trusted operation/receipt linearization point and commit journal, explicit key rotation and rollback protection, crash/reboot/fault injection, and independent security signoff. The earlier SUP-27 same-UID authority and HMAC forgery reproductions remain valid for actors with root/fixture-owner privileges. CI passing the new test proves only distinct-UID **signing-key custody and cryptographic binding** under this limited threat model.

**Do not merge PR #1039. Do not enable `UnavailableScopedMutationService` alternatives. Maintain GE-04 SECURITY HOLD.**
