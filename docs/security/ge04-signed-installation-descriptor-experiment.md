# GE-04 — descriptor-pinned signed installation experiment

**SECURITY HOLD. No helper execution, production trust anchor, or admission.**

`experiments/ge04/signed-installation.py` opens one installation directory descriptor with `O_DIRECTORY|O_NOFOLLOW`, requires an expected owner UID and rejects group/other-writable directories. It reads `trusted.pub`, `manifest.json`, `manifest.sig`, and `helper` using `openat`-style `dir_fd` and `O_NOFOLLOW`; requires regular, single-link, non-writable owner-matched inodes with bounded sizes and stable metadata; and passes the bytes to the existing Ed25519 signed-release verifier. This removes per-file pathname reopening inside the installation, but not ancestor-path replacement, same-UID modification, or atomic multi-file snapshot concerns.

`python3 -B experiments/ge04/test-signed-installation.py` verifies valid input and denies writable helper, symlink signature, and writable installation directory. The initial experiment **deliberately demonstrated a same-UID attacker replacing both the public key and signature and still passing** when no independent trust anchor was provided. The next bounded revision requires an externally pinned SHA-256 digest of the public key and rejects that substitution, provided the digest is independently trusted. The privileged CI test `test-signed-release-root.py` now additionally verifies descriptor-pinned installation under root and cross-UID worker write denial. CI qualification of this new change remains pending.

The pinned key digest is currently a function argument supplied by the test harness; it is **not** yet loaded from an administrator-controlled configuration. A worker allowed to select this digest can still substitute the trust anchor. This prototype also accepts caller-selected installation path and owner UID for testing. Production must fix both through privileged configuration, independently pin the public-key digest outside worker-controlled state, validate every ancestor and deployment mount, use an atomic signed-release generation, and enforce rollback/version policy. The helper bytes are verified but not passed into the sealed-memfd preflight in this experiment. Neither file DAC nor Ed25519 signatures alone solve supervisor compromise or crash-safe authorization.

## Signed installation → sealed snapshot handoff (experimental)

`prepare_verified_sealed_helper` reuses the descriptor-pinned installation reader and Ed25519 verifier to obtain the **same verified helper bytes** alongside the signed digest. It copies those exact bytes into a Linux `memfd_create(MFD_ALLOW_SEALING | MFD_CLOEXEC)` descriptor, independently rehashes the snapshot, then applies and verifies write/grow/shrink/seal seals. The API returns an owned descriptor that the caller must close; it **does not execute** the helper or authorize a filesystem mutation.

`test-signed-sealed-installation.py` checks wrong release/key-pin denial, signed snapshot sealing and mutation rejection, same-inode alteration of the original helper after sealing, and rejection of a subsequent verification of that tampered installation. This joins signature verification to sealed bytes without a second pathname read. The branch-restricted GE-04 CI lane executes this fixture.

**Limitations:** The trusted-key digest, expected release and installation path remain caller-supplied test inputs, not administrator-controlled authority. Files are read separately under one pinned installation directory rather than from an atomic release generation. No protected supervisor session, verified child identity, final-boundary policy/lease fence, authenticated durable terminal receipt, anti-rollback policy, crash reconciliation or production launch is implemented. A signed-and-sealed snapshot is *code integrity evidence only*, not execution authorization. SECURITY HOLD and the production unavailable backend remain unchanged.
