# GE-04 — Protected supervisor installation and launcher fixture

**SECURITY HOLD: isolated Linux experiment only. Not a production service manager, launch attestation, or mutation authority.**

The prior endpoint tests proved that a distinct-UID coordinator cannot manipulate a protected root-owned supervisor socket, but did not check the executable/configuration bundle used at supervisor startup. `experiments/ge04/protected-supervisor-installation.py` verifies an explicit root-owned 0700 installation directory, an exact set of root-owned regular 0600 modules, and a root-owned 0600 installation manifest with SHA-256 digests of those modules. It rejects malformed manifest, duplicate fields, symlinked modules, hardlinked modules, changed metadata, unexpected digest and unsafe file ownership/modes. After verification, a root process launches the **inert** supervisor using Python isolated mode `-I`, with no inherited application descriptors. The fixed service implementation still permits only the prior inert datagram, using per-message kernel-attested sender PID/UID and protected state/credential/observation files.

`test-protected-supervisor-installation-root.py` constructs a privileged test-only install, proves module tampering and manifest version changes are rejected, runs a separately exec'd UID/GID 65534 coordinator that must be denied modification of the installation manifest/modules, directory permissions, or protected authority state, verifies its single inert request reaches the root supervisor and consumes the fixture approval, and verifies restart with an orphaned endpoint fails closed rather than resetting consumed authority. The root-only regression is included in the `ge04-cross-uid-denial` CI job.

## Explicit limitations and release blockers

- **No real OS service manager is installed**: launch remains initiated by a root-run test provisioner; it is not a systemd unit with installation/upgrade authorization, sandboxing, restart limits or audited privileged recovery. An untrusted coordinator that can obtain root-equivalent privileges can bypass the test fixture.
- SHA-256 manifest integrity is **not independent authenticity**: root provisioner controls both the modules and manifest. An attacker with root write privileges can replace both. A pre-launch check followed by ordinary path-based Python execution is not a race-free kernel-enforced executable identity pin; production launch must close that TOCTOU gap or bound it under a separately justified threat model.
- Protected directory checks cover final installation directory and files; trusted ancestor-chain validation and atomic install/upgrade/rollback are not demonstrated by this fixture. The runtime Python interpreter, Python dependencies, and OS provenance are not pinned by the manifest.
- The fixed test request is not a real authorized filesystem operation. SUP-25/SUP-26 remain inert fixtures, and their terminal marker is not an authenticated real-effect receipt. No actual mutation path is connected. Additional denial, recovery, fault-injection and independent review remain required.
- Previous SUP-27 same-UID state/receipt forgery findings remain valid when the attacker can access the supervisor's protected root. The distinct-UID test narrows the threat model; it does not make supervisor authority nondelegatable against a privileged attacker.

PR #1039 remains open/unmerged. `UnavailableScopedMutationService` stays disabled until installation custody, final-boundary real-effect enforcement, authenticated durable receipts, and independent review are completed and signed off.
