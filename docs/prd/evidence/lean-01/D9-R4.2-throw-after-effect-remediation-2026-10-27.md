# D9 R4.2 — Post-effect throw ambiguity remediation (2026-10-27)

## Scope

Branch `fix/d9-phase-f-security`, based on `76ca705d`. This is implementation evidence, not independent Phase F sign-off.

## Defect and conservative resolution

Previously, both ordinary dispatch and approved continuation resume recorded a `failed` execution receipt when the downstream router threw, even if the router had already applied an external effect. A thrown exception alone cannot prove the absence of that effect.

Both executor catch paths now preserve a consumed claim as `pending` on a non-cancellation router exception. Explicit cancellation continues to record `cancelled`. A normal returned success, error, or `outcomeUnknown` result retains its existing receipt semantics. Pending claims remain fail-closed and are eligible for `unverified` classification rather than replay of the single-use authorization.

## Adversarial regression

`tests/security/continuation-unknown-outcome.vitest.ts` adds ordinary-dispatch and continuation-resume cases in which `file.create` applies a real file effect and the adapter then throws. Both cases assert the real file exists and the consumed approval remains `pending`. The focused suite passed **9/9** in the initial post-change run (`/tmp/alix-d9-throw-tests2.log`).

## Qualification limits

- This does not prove exactly-once external effects, transactional coupling, or idempotency of third-party adapters.
- Exception paths now deliberately favor an unresolved claim over a potentially false failure receipt. Operators must reconcile uncertain external effects.
- Broader security suites, static checks, and independent review must complete before any gate promotion.
