## A-1 — assignment identity invalidates continuation and recovery

- `worker-tool-continuation.ts` captures the original worker assignment's `assignedAgentId` in host attribution. `PendingContinuation.coordinationWorker` and `ApprovalRecord.toolContinuation` retain it. It is optional in the persisted types for readability of legacy records, but required for daemon authority.
- Assignment identity is **separate from canonical tool invocation identity**. Existing execution paths can use a tool agent different from the assigned agent (for example, a subagent task ID). Comparing current assignment directly with that tool agent would reject valid work, and replacing the tool agent would change the invocation/lease authority. The fix compares the original assignment snapshot with current durable `worker.agentId`, retaining the original tool agent, invocation fingerprint and worker consumer attribution unchanged.
- The shared worker predicate checks assignment identity and the worker's run identity. Initial eligibility, periodic monitoring, the pre-resume re-read, and success/failure worker updates use it. The restricted approval consumer re-reads durable context again immediately before claiming a grant. Context loss aborts and refuses consumption. Successful-receipt recovery checks assignment identity both before and inside its locked worker update.
- `ToolExecutor.bindContinuationWorker` refuses replacement of an existing differing attribution snapshot. A new assignment cannot rebind the paused operation to reuse its grant. Missing legacy assignment snapshots stay blocked; they are never inferred from the tool agent or current worker. This is an intentional fail-closed compatibility limit, not an automatic migration.
- Executed regressions cover reassignment before claim and after claim/before dispatch; distinct assigned/tool-agent positive control; changed/missing canonical identity; missing assignment; denied rebinding; fresh-process SIGKILL recovery after a successful receipt with reassignment; and reassignment between recovery's initial eligibility check and its run-lock acquisition. The locked recovery test preserves the full worker/effect/receipt snapshot and detects router re-entry.
- The full-daemon `F-A-pre-owner` expectation now requires prevention and unconsumed authority after observed cancellation. **All post-router-entry stale-effect expectations remain unchanged**, including `F-A-effect-owner`. These socket cases did not reach their assertions here. Periodic observation and the extra claim check do not linearize durable authority changes with arbitrary effects: a change after the last check/router entry may still produce an effect. No stronger prevention or exactly-once guarantee is claimed.

## A-2 — finishing stop preserves successor publication

- `daemon-server.ts` acquires the shared global `~/.alix/daemon-lifecycle.lock` using the existing portable `ApprovalStoreLock` backend before admission/publication and holds it through process death. That includes startup, ping repair and heartbeat writers, even when explicit socket paths differ under the same HOME. Existing socket admission, live-socket protection and server-only socket cleanup remain intact.
- The server deliberately leaves the lock record for proven-dead-owner reclamation. Releasing from an exit callback could admit a successor while the old process or pending filesystem I/O still exists. Live/unprovable owners are not stolen by age; malformed metadata, missing ownership evidence or PID reuse can block availability and require operator recovery. The implementation relies on the existing lock primitive and its platform contract; this is not a new independent audit of that primitive.
- After verifying old-process exit, `DaemonManager.stop` acquires that same lock. Contention/unprovable ownership leaves metadata untouched. Under the lock it rechecks PID, start timestamp and socket identity before publishing stopped status, and removes the PID projection only if it still names the stopped PID. A successor cannot publish between this check and the write/removal because its server must hold the same lock. Stops never unlink the socket.
- Stop also rejects non-positive, non-integral and non-finite PIDs before any signal or process probe. The existing one-pong explicit mismatch rejection and PID-less legacy command-line verification remain unchanged. This does not claim an atomic OS PID handle or cryptographic peer authentication.
- A deterministic regression runs a real independent metadata publisher at the old-exit/final-publication boundary. Both a live successor holding the lock and an already-published successor that released it retain their exact JSON and PID metadata. The held-lock case verifies the successor's lock was not stolen. Only old pong/liveness is simulated; no nonzero signal reaches a real process. Existing sequential stop/start coverage now also checks stopped-owner identity, PID projection removal and restarted-owner publication.
- Participating server/manager versions must share this lock contract. Concurrent legacy binaries that do not participate are not qualified. Socket-free publication tests are not a substitute for Linux/macOS live-daemon lifecycle qualification.
