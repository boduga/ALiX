[The process-race record](D9-R4.2-process-race-qualification-2026-10-27.md)
left the full-daemon matrix as an unimplemented design and said so explicitly:
"the preload and daemon-task cancellation fixture in steps 2–5 remain to be

plus `tests/fixtures/d9-full-daemon-preload.ts` and
`tests/fixtures/d9-full-daemon-actor.ts` implement that design. The private
Unix-socket bind now succeeds on this host, so the executable actually ran.

The harness is an OS-process test, not a mock: it spawns the compiled
`src/operations/daemon/daemon-server.js`, requires the real
`Daemon listening on …` line **and** a JSON-line `ping`/`pong`, and asserts a
live PID with `kill(0)`. Disposable workspace and `HOME`; no provider is
called (offline `scripted-mock` config, `subagents.enabled: false`).

The test-only `--import` preload wraps production methods **after** they run
and parks at named checkpoints. It never substitutes an allow/deny result,
consumes on behalf of a gate, or injects a cancellation controller. The
`FileToolRouter` wrapper appends an explicit external-effect surrogate after a
successful file creation — outside the approval ledger transaction — and is
documented as such. Security boundary code and durable stores are real.

## Result: three production defects, all reproduced before being fixed

The first full run was **30/37**. One failure was intermittent and was
reproduced separately; the other three are deterministic.

| Case | Defect | Evidence before the fix |
|---|---|---|
| `F-E-unknown`, `F-E-timeout-applied` | An authorized call that reached no provable terminal outcome recorded `failed` on the **continuation** route | `approval.executionOutcome` was `failed`; both routes were expected to leave `pending` |
| `F-C01` | A cancelled task was overwritten to `completed` on the non-agent route branch | Durable `daemonTask` ledger went `cancel_requested` → `completed`, and restart kept `completed` |
| `F-E-duplicate-keyed` (intermittent) | A lock left by a `SIGKILL`ed owner blocked every approval mutation | `mutate()` polled 10 s then threw `Could not acquire approval lock`; aged-out only after 60 s |

### 1. Unknown outcome must write no receipt on either dispatch route

`ToolExecutor.dispatch` already documented the rule: an `outcomeUnknown` result
"must NOT record either a success or a failure execution receipt", and the
claim stays `pending` so a later replay classifies it `unverified`. That block
sits after dispatch, and the `source === "continuation-resume"` branch returned
earlier — so the same adapter result produced `consumed`/`failed` through a
resume, permanently retiring a single-use approval that may in fact have applied
its effect. The fix applies the same tri-state rule on the continuation branch.

Fail-closed direction is preserved: `succeeded`/`failed`/`cancelled` receipts are
unchanged for known outcomes, and `pending` is never promoted by this change.

### 2. An accepted cancellation must never be overwritten by success

`handleRun`'s non-agent branch wrote `status: "completed"` unconditionally after
`executeRoute`. The agent branch already checked `cancel_requested`, and the
`cancel` command already committed `cancel_requested` durably with a real abort,
so the route branch silently reversed the operator's decision — and the ledger
kept it across restart. Both branches now record `cancelled` in that state.

### 3. A dead lock owner is proof enough

`ApprovalStoreLock.isStale` required **both** an age gate and a dead PID, in that
order. A daemon killed inside `mutate()` therefore left a lock that was respected
for the full 60 s ceiling; every approval mutation meanwhile polled to its 10 s
timeout and threw. During crash recovery that is the whole recovery path —
`expireDue`, `consumeApproved`, `recordExecutionOutcome` — so recovery stalled
indefinitely. Either proof now breaks the lock, matching `audit-lock.ts`. A lock
directory with no `meta.json` is still respected, so the create-then-write window
cannot be stolen.

## What this qualifies, and what it does not

Qualified here: the full socket daemon executable participating in approval
claim contention, lease preservation against an independent resumer, the
requested/effect authority-change matrix, public-IPC task cancellation across
restart, controlled effect adapters, and real `SIGKILL` at each resumer
checkpoint with fresh-process recovery. The asserted invariants do not depend on
which PID wins.

Still NOT qualified: interruption inside a ledger/fsync commit; immediate
prevention between a durable authority change and its 100 ms observation (the
dispatch rows deliberately wait for the observed abort); linearizability of a
filesystem or external effect against revocation; every instruction boundary;
remote idempotency; forged receipts; machine power loss; and the independent
review itself. The effect surrogates remain surrogates — a fixed idempotency key
and a double `sendIndex` model adapter behavior, not a real remote API,
plugin or shell effect. No distributed transaction and no universal
exactly-once guarantee follows. **No assertion here closes the forged-receipt,
arbitrary-network-effect or independent-review gaps.**
