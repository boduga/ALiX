## 4. Findings

### F-1 — HIGH — `alix daemon start` unlinks a live daemon's socket before any admission check

Locations:

- `src/operations/daemon/daemon-manager.ts:74-75` — unconditional `rm(socketPath)` before spawn.
- `src/operations/daemon/daemon-manager.ts:106-111` — failure path removes pid/status/socket again.
- Reachable from `src/interfaces/cli/commands/daemon-audit.ts:19-21` (`alix daemon start`).
- Contract it violates: `src/operations/daemon/daemon-server.ts:644-646` ("Never unlink a live
  daemon's socket") and `src/operations/daemon/AGENTS.md` (exclusive daemon admission).

Reproduction (real processes, production build, tmpfs):

```text
daemon_A_started= true pid= 6388
ping_before= {"type":"pong"}
socket_inode_before= 25
manager_start_error= "Daemon failed to stay running after start. Run daemon-server directly for logs."
socket_inode_after= MISSING(ENOENT)
daemon_A_alive= true
ping_after= ERROR:ENOENT
VERDICT_live_socket_preserved= false
```

Daemon A stayed alive and healthy, but its socket pathname was deleted, so every client — CLI,
Inspector, scheduler — lost the daemon. The second daemon correctly refused admission
(`daemon-server.ts:655-659`), so the admission lock itself works; the manager destroyed the live
socket **before** the lock could arbitrate.

Why 38/38 full-daemon tests did not catch it: `tests/security/d9-full-daemon.test.ts:111-127`
(`F-R01`) spawns `daemon-server.js` directly (`daemon()` helper, lines 297-302) twice. Both contend
on the lock and the assertion "live socket must not be replaced" passes. The production CLI path is
never exercised.

Second trigger: `DaemonManager.stop()` (`daemon-manager.ts:118-134`) writes `status: "stopped"`
before the process has exited. A `start()` issued in that window sees `status !== "running"`, skips
the stale-cleanup branch (lines 53-69), and reaches the same `rm` while the old process is still
serving. That ordering is F-5.

Impact: local denial of service and state loss for a single-user local daemon — an operator command
destroys a working daemon. No privilege escalation, no cross-user exposure.

### F-2 — MEDIUM — an initially unbound approval is claimable, and its receipt reportable, by any worker port

Locations:

- `src/governance/approvals/worker-approval-port.ts:176-178` — visibility admits any record with no
  `workerId`, regardless of session or coordination run.
- `src/governance/approvals/worker-approval-port.ts:193-198` — the port forwards the caller's
  `consumer` after injecting only `workerId`.
- `src/governance/approvals/approval-store.ts:1000-1015` — `consumeApproved` enforces worker binding
  only when the record has one; an unbound record is consumable by anyone, and the claim writes
  whatever `consumer.workerId` the caller supplied.
- Creation shape: `approval-store.ts:638-656` (`request()`) has no `workerId`/`workerAttempt`
  parameter, and the worker executor's gate call (`src/capabilities/tools/executor.ts:657-668`)
  passes `ownedPaths` but no coordination identity. Coordination dispatch approvals are bound
  (`policy-gate.ts:808-821`); **worker tool approvals are not**.
- Recovery that then refuses: `src/operations/daemon/tool-continuation-resumer.ts:183-196`
  (`recoverSucceeded` requires `consumedByWorkerId`/`consumedAttempt` to equal the host context).

Reproduction (discovery without an id, cross-session theft, forged receipt):

```text
discovered_without_id= true victim_session= session-victim victim_run= null status= approved workerId= null
cross_session_consume= true reason= null
durable_consumer= "worker-b" attempt= undefined status= consumed outcome= pending
thief_receipt_succeeded= true
durable_final_outcome= succeeded
victim_consume_after_theft= false reason= status is consumed
bound_visible_to_sibling= false
bound_consume_denied= true reason= worker mismatch
```

A second probe reproduced the same on a D9-shaped record (approval created by the real executor in
`ask` mode, then approved): `sibling_consume_consumed=true`, `sibling_receipt_accepted=true`,
`owner_receipt_accepted=false`, `final_outcome=succeeded`.

Discovery needs no prior knowledge of the id: the port's own `findResolved({ capability })` returns
the newest non-pending record whose `workerId` is empty, together with its `bindingKey` and
`invocation`. Both are stored in cleartext on the record.

The race window is real, not theoretical. The legitimate claim happens when
`ApprovalWatcher.scan()` (`src/operations/daemon/approval-watcher.ts:82-87`) reaches the record on its
30 s interval (`intervalMs` default `30_000`, line 42) and the resumer then binds and consumes it. A
worker polling faster than the watcher can win that window. Once it wins, the record is
`consumed`/`pending`, which the watcher's filter (line 83-84) does **not** revisit, so the legitimate
continuation is never retried and the worker stays `blocked` indefinitely — the same outcome whether
or not the thief also reports a receipt.

What an attacker gains: the single-use operator grant is spent by the wrong worker. The legitimate
worker can no longer execute (`executor.ts:518-521` requires `status === "approved"`; it is now
`consumed`), cannot be requeued (`recoverSucceeded` sees a different consumer), and the ledger
records a durable `succeeded` outcome for an effect that never happened. The thief cannot execute
the approved effect: it has no continuation host, its own invocation differs, and consumption
precedes execution.

Severity rationale: this is a containment failure of the boundary the restricted port exists to
enforce ("a compromised worker could grant itself any capability"), with durable evidence
corruption. It is **not** model-tool-reachable — no offered tool calls `consumeApproved` or
`recordExecutionOutcome` with an arbitrary id — so it needs a worker process that can invoke the port
(compromised worker, or a future tool/plugin that reaches it). That is why it is MEDIUM and not
HIGH; the original finding A (§5), which needed no claim, was HIGH and is fixed.

The relevant DOX sentence — "an initially unbound tool approval does not permit another worker to
forge its receipt" — is true only for a *third* worker after consumption. The consumer wins the
claim first and then reports its own receipt.

### F-3 — MEDIUM — the restricted port does not propagate `workerAttempt` into consumption

Location: `src/governance/approvals/worker-approval-port.ts:193-198`. The port injects `workerId`
but never `workerAttempt`, while `recordExecutionOutcome` and `markExecutionUnverified` (lines
199-203) do inject both.

Reproduction:

```text
same_worker_same_attempt_via_port= false reason= worker attempt mismatch
unbound_consumed= true recorded_attempt= undefined port_attempt= 7
```

Two consequences:

1. A worker holding an **attempt-bound** approval cannot consume it through its own port at all —
   the store sees `workerAttempt: 1` vs `consumer.workerAttempt: undefined` and denies
   (`approval-store.ts:1003-1005`). Latent today because worker-created tool approvals are unbound
   (F-2), but it blocks the natural remediation of F-2 (binding identity at creation) unless fixed
   in the same change.
2. An unbound approval consumed through a port with an attempt records `consumedAttempt:
   undefined`, silently dropping attempt attribution. The D9 host path is unaffected because the
   resumer wraps `consumeApproved` and injects both values
   (`tool-continuation-resumer.ts:124-130`); the generic worker port is affected.

### F-4 — MEDIUM — daemon admission depends on the util-linux `flock` binary with no fallback

Location: `src/operations/daemon/daemon-server.ts:648-659`.

Reproduction with the binary unavailable:

```text
EXIT=1
[daemon] socket owner is active or lock unavailable; refusing startup /dev/shm/flocktest/alixd.sock
```

The behaviour is fail-closed (correct security posture) but makes `alix daemon start` unusable on a
supported platform: stock macOS ships no util-linux `flock(1)`, so `spawnSync` returns ENOENT and the
daemon refuses every start. This was reasoned from the code plus the executed missing-binary probe;
it was **not executed on macOS**. The macOS CI lane (`ci.yml:191-209`) runs only
`pnpm test:vitest`, which does not collect the `node:test` daemon suites, so this is not caught by CI.
On Windows `isNamedPipe` skips the admission block entirely; libuv `FIRST_PIPE_INSTANCE` behaviour was
not verified (network fetch unavailable) and remains **unqualified**.

The approval store itself has a `mkdir` fallback (`detectLockBackend` in
`approval-store-lock.ts`); the daemon admission does not.

### F-5 — LOW — `DaemonManager.stop()` records `stopped` before the process exits

Location: `src/operations/daemon/daemon-manager.ts:118-134`. SIGTERM is sent, `status` is rewritten
to `stopped`, and the pid file is removed without waiting for exit or socket cleanup. Combined with
F-1 line 75 this creates a second way to unlink a live socket: `stop()` immediately followed by
`start()`.

## 6. Area-by-area requalification

- **A. Approval receipt authorization.** Worker/attempt binding at outcome time is correct and
  fail-closed. Consumed-claim ownership is enforced for reporting. Two gaps: unbound claims are
  stealable (F-2), and the port drops attempt at claim time (F-3).
- **B. Cancellation and execution authority.** Pre-dispatch checks exist at both required points;
  cancelled claims are never restored; a pre-claim cancellation leaves authority untouched.
  Lease/ownership changes abort via the 100 ms monitor and the 10 s renewal. Residual: the window
  between the final check and the router effect.
- **C. External-effect uncertainty.** Thrown router exceptions and `outcomeUnknown` results leave the
  claim `pending`; only explicit cancellation records `cancelled`. No exactly-once claim is made
  anywhere, and none is supported: effects are non-transactional filesystem/external calls.
- **D. Daemon socket ownership.** `daemon-server` admission is correct: exclusive `flock`, competing
  daemon rejected, live socket preserved, SIGKILL releases the lock, stale socket removed only while
  holding the lock, lock pathname re-verified by dev/ino (`daemon-server.ts:660-666`). The
  `DaemonManager` start path bypasses all of it (F-1), and admission has no non-`flock` fallback
  (F-4).
- **E. Crash recovery and concurrency.** All seven checkpoints (`before-resume`, `after-tombstone`,
  `after-consume`, `after-effect`, `after-receipt`, `during-reconciliation`, `after-effect`
  duplicate) pass in the full-daemon suite; independent-process contention and SIGKILL recovery pass.
  Recovery refuses mismatched consumer identity, which is what turns F-2 into permanent stranding.

## 7. Residual risks and limitations

1. **No exactly-once external effects.** Nothing in this review establishes transactional or
   downstream idempotency for arbitrary tools. A crash after an effect and before the receipt leaves
   the claim `pending`/`unverified`; the effect may have happened. `RISK-REPLAY-01` stays OPEN.
2. **Sub-100 ms cancellation window.** The executor checks the signal immediately before dispatch,
   but a router that has begun a write cannot be interrupted. Cooperative cancellation only.
3. **F-2 threat model.** Not reachable from the model-facing tool surface; requires a worker process
   able to call the restricted port. Treated as a containment defect, not an escalation.
4. **Attempt attribution.** Attempt-bound consumption through the generic worker port is impossible
   today (F-3); any remediation that binds approvals at creation must fix it in the same change.
5. **Platform coverage.** macOS daemon startup is fail-closed but unusable (F-4); Windows named-pipe
   exclusivity is unverified; the D9 suites are Linux-only and `node:test`-only, so the macOS CI lane
   does not exercise them.
6. **Host I/O sensitivity.** Daemon startup performs synchronous disk work; on a saturated disk the
   socket can appear hung for tens of seconds. Environment, not a defect, but it makes timing-based
   tests unreliable without tmpfs.
7. **Test-harness coverage gap.** The full-daemon suite validates the server executable, not the
   operator CLI entry point. F-1 lives exactly in that gap.
8. **GitNexus staleness.** Index 54 commits behind; `recordExecutionOutcome` unresolved. Graph
   conclusions are advisory here; probes are primary.

## 9. Next actions (prioritized)

1. **Fix F-1**: move socket removal behind the admission decision. Either have the manager probe the
   lock/admission first and never unlink on refusal, or delete the manager-side `rm` and let
   `daemon-server` own stale-socket cleanup under the lock it already holds
   (`daemon-server.ts:669-670`). Add a regression that starts a real daemon through
   `DaemonManager.start()` (not `daemon-server.js`) and asserts the live inode and `ping` survive.
2. **Fix F-2/F-3 together**: bind `workerId`/`workerAttempt` when a worker-originated approval is
   created (inject both in the port's `request`/`requestOrReusePending` path), or make worker ports
   refuse to consume unbound records while the host binds them under the run lock before resuming.
   Extend the parity table with: sibling port cannot discover, consume, or report on an unbound
   approval from another session/run.
3. **Fix F-4**: give daemon admission a fail-closed fallback for platforms without util-linux
   `flock` (the `ApprovalStoreLock` `mkdir` backend is the existing precedent), or state the
   supported-platform restriction explicitly and enforce it at startup with a clear message. Add the
   `node:test` daemon suites to a platform lane that actually runs them.
4. **F-5**: make `stop()` wait for exit (bounded) before writing `stopped`/removing the pid.
5. Re-run this requalification after the fixes; treat green suites as necessary, not sufficient.
6. Keep `RISK-REPLAY-01` open until an adapter-level transaction or idempotency contract exists.
