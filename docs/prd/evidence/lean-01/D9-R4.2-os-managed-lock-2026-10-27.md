# D9 R4.2 — OS-managed crash-safe approval-store lock (Phase F) — 2026-10-27

## Scope and provenance

- Branch: `fix/d9-phase-f-security`. No merge, no push, no gate decision authorized.
- Replaces the atomic-`mkdir` + PID-liveness approval lock (and its fail-closed
  uncommitted patch) with an OS-managed lock: an exclusive advisory `flock` that
  the kernel releases automatically when the holding process exits — including
  `SIGKILL`. This closes the remaining uncertainty the stale-lock remediation
  recorded as "not eliminated without an OS-released lock primitive".
- The uncommitted fail-closed changes (remove age-based reclaim) were inspected
  and deliberately superseded: their safety posture is preserved as the
  documented fallback backend, but the OS-managed lock removes the age/PID
  staleness model entirely on the primary platform.

## What changed

- `src/governance/approvals/approval-store-lock.ts` — `ApprovalStoreLock` is now a
  facade over two backends, selected once per platform by `detectLockBackend()`:
  - **`flock` (primary, Linux/BSD):** the holder `open`s `.alix/approvals/approvals.lock`
    and asks the util-linux `flock` binary (file-descriptor form, `flock -n -x <fd>`)
    to lock it. The lock lives on the open file description the holder keeps open,
    so the kernel releases it on any holder exit — no PID probing, no age, no
    reclaim step. Acquisition is a non-blocking poll loop reusing one fd.
  - **`mkdir` (fallback, macOS/Windows):** the prior atomic-mkdir lock, made
    fail-closed: a provably dead PID is reclaimed immediately, a provably alive
    PID is never reclaimed, and an unprovable owner is never reclaimed by age.
- `tests/approvals/approval-store-lock.test.ts` — 22 in-process cases: flock
  acquire/release/blocking/reacquire + legacy-directory tolerance + the full
  fail-closed mkdir-fallback matrix.
- `tests/security/approval-lock-liveness.test.ts` — 6 real OS-process cases:
  paused (SIGSTOP) writer, SIGKILLed dead owner, concurrent contenders, daemon
  restart, and two mkdir-fallback cross-process reclaim cases.
- `tests/fixtures/d9-approval-lock-child.ts` — accepts an optional backend so the
  mkdir fallback is exercisable as a real OS process.
- `src/governance/approvals/AGENTS.md` — the lock contract rewritten for the
  OS-managed primary and the fail-closed fallback.

The four required adversarial OS-process scenarios are all exercised against
real independent processes:
- **Paused writer** — a holder frozen with `SIGSTOP` keeps its kernel lock; a
  contender's `acquire(400)` returns `false` (never stolen).
- **Dead owner** — a holder killed with `SIGKILL` releases immediately; a
  successor acquires in under 1 s with no age/reclaim step.
- **Concurrent contenders** — six hosts serialize a read-modify-write; the final
  counter equals six (no lost update, no double-steal).
- **Daemon restart** — a SIGKILLed daemon is followed by a restarted daemon that
  acquires immediately (no orphan-lock recovery).

## Unresolved limitations

1. **`flock(1)` is Linux/BSD-only.** macOS and Windows CI (and any non-flock
   platform) select the `mkdir` fallback, which is fail-closed but cannot
   auto-release an unprovable orphan — an invalid/missing PID or a missing/
   malformed `meta.json` left by a kill between `mkdir` and the metadata write
   requires explicit operator recovery. The OS-managed auto-release guarantee
   therefore holds only on the primary (Linux) platform.
2. **The lock is held by an in-process fd via a child `flock` invocation, not a
   native syscall.** Node exposes no `flock`, so acquisition spawns one short
   `flock` child per non-blocking attempt and one fd is held for the lock's
   lifetime. This is correct (the child exits immediately after locking; the
   holder's own fd keeps the lock) but adds a per-acquisition subprocess. It is
   bounded and acceptable for approval mutations, which are not a hot path.
3. **PID reuse is moot for `flock` but not for the fallback.** On the primary
   path there is no PID identity at all, so recycled-PID liveness confusion
   cannot occur. The fallback retains the prior fail-safe posture: a valid PID
   that reads alive is never reclaimed, so a recycled PID there stalls until
   manual cleanup — fail-safe, never theft.
4. **Advisory, not mandatory.** `flock` only serializes callers that take the
   same lock; every approval mutator goes through `ApprovalStoreLock`, but a
   process that bypasses it (or deletes the lock file mid-hold) is not blocked.
   This is unchanged from the prior `mkdir` lock and is inherent to advisory
   locking.
5. **Cross-platform process tests run only where `flock` exists.** The four
   adversarial OS-process cases execute on Linux; the macOS/Windows lanes run
   the vitest approval suites (which exercise the in-process `flock`-or-`mkdir`
   path) but not the real-SIGKILL lock liveness suite, because there is no
   `flock` binary there to exercise.
6. **Cross-version migration.** A leftover DIRECTORY at the lock path (an
   orphan from the pre-flock `mkdir` lock) is opened read-only and flocked, so
   the new backend does not throw; but a live old-version daemon holding the
   `mkdir` lock does not share mutual exclusion with a new-version `flock`
   daemon on the same path. Upgrade requires quiescing old-version daemons
   first (advisory locks only serialize callers using the same primitive).

## Follow-up: lock-path inode validation (2026-10-27)

- A successful `flock` acquisition now compares `fstat(fd)` with `stat(lockPath)`
  and refuses success when device/inode identities differ. This prevents an
  acquisition already waiting on an unlinked inode from reporting ownership.
- A focused adversarial test unlinks and replaces the pathname while a contender
  waits on the original holder, then releases the original. The contender must
  reject the obsolete inode. The focused lock and real-process suite passed
  **28/28** after this change.
- **Not a complete pathname-replacement defense:** an actor with permission to
  unlink or replace the lock path *after* validation can still create distinct
  inode lock domains. Restrict directory write permissions and forbid cleanup,
  rotation, or replacement of `approvals.lock` while any daemon is active.
  Quiesce all legacy `mkdir` daemons before switching to `flock`.
- This is additional evidence, not independent Phase F requalification.
