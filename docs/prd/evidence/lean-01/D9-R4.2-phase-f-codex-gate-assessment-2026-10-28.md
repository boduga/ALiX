## 4. Remaining findings and risks

### A-1 — MEDIUM, gate-blocking authority gap: agent reassignment does not invalidate a continuation

`src/operations/daemon/tool-continuation-resumer.ts:61` compares worker ID, attempt, approval and scope with the captured continuation, but omits `worker.agentId`. The monitor uses this same predicate. Execution deliberately substitutes the captured original agent for lease acquisition and dispatch, so changing the current assignment's agent does not abort it. The recovery eligibility predicate also omits this comparison.

Independent execution of the actual compiled predicate, checked against a fresh compilation of HEAD, produced:

```text
CURRENT_AGENT_CHANGED_ELIGIBLE=true
CURRENT_ATTEMPT_CHANGED_ELIGIBLE=false
```

The new probe uses synthetic run/continuation objects and performs no effect. Separately, `tests/security/d9-full-daemon.test.ts:223–239` changes the durable worker agent to `replacement`; its `F-A-pre-owner` case deliberately requires a consumed approval and an actual stale file effect. That exact test is green in the supplied qualification log. The source, predicate probe and historical process characterization agree; this is not a new live-daemon reproduction in this session.

Impact is use of original execution identity after assignment identity changed, undermining a broad claim of current worker authority. This does not demonstrate a model-facing self-escalation path: changing durable worker assignment requires host/store authority. Nevertheless, the requested current-context security guarantee is not met. Resolve the invariant with a prevention regression, or obtain an explicit operator-owned scope decision explaining why agent reassignment preserves the original grant. A clean narrow diff review does not dispose of it.

### A-2 — MEDIUM availability/lifecycle defect: a stopping manager can erase successor metadata

After proving the old PID exited, `daemon-manager.ts:210–212` writes a snapshot of the **old** status as stopped and removes the PID file. It does not check whether a new server has meanwhile published its identity. The server publishes after admission/listen; daemon admission serializes servers, not the manager's later status writes.

New synthetic interleaving, using the real `stop()` method with simulated pong/liveness and real disposable metadata files:

```text
successor:   pid=123456790 status=running
finalStatus: pid=123456789 status=stopped
pidFileExists=false
```

The probe never sends a signal or binds a socket. It injects successor publication as the old process becomes absent; it establishes unconditional metadata clobber, not its incidence in a live OS race. The reachable interleaving is inferred from independent manager/server processes and the lack of a shared lifecycle lock/CAS. Existing sequential stop-then-start tests do not cover it.

A live successor can remain reachable while status says stopped; a subsequent `stop()` returns early. Ping repairs metadata only when `daemon.json` is absent, not when it is present but stale/stopped. Treat lifecycle readiness as failed until owner-safe publication is demonstrated or this limitation receives an explicit disposition. No escalation or arbitrary-PID signal was demonstrated by this probe.

### A-3 — Major qualification blocker: macOS has a configured lane, not measured coverage

The new `daemon-macos` job runs only `dist/tests/daemon/daemon-manager.test.js`. No successful run at HEAD is in the supplied material. Even a green job would not execute the full D9 daemon/resumer/process-race suites or durable completion/restart suite.

Required evidence before a cross-platform readiness claim:

1. Retain a successful macOS job bound to the reviewed commit, OS/architecture, Node, dependency lockfile and exact commands. Confirm the tested backend is mkdir; an installed flock must not silently replace fallback coverage.
2. Execute actual admission/contention, SIGKILL stale-owner recovery, orderly stop/restart, legacy PID-less verification and explicit mismatch refusal. Include live/missing/malformed lock metadata and backend-transition refusal.
3. Execute the D9 process/crash matrix and corrected durable-completion probe on macOS, or explicitly declare and disposition the narrower platform qualification. Tests registered in Linux logs are not macOS results.
4. Exercise concurrent lifecycle publication and current-agent invalidation after resolving A-1/A-2.

Windows named-pipe admission skips the POSIX block; its exclusivity and restart behavior remain unqualified here. Existing Windows Vitest CI does not establish compiled daemon coverage. Report Windows separately if it is within the intended release scope.

### A-4 — Retained limits must remain visible

- **RISK-REPLAY-01 stays OPEN.** Single-use invocation authority does not provide transactions or idempotency for shell/API/plugin/provider effects, changed invocation identities or bypass operations. A crash after the effect but before a receipt leaves ambiguity. No external exactly-once conclusion is supported.
- **After-router-entry authority changes:** the characterization tests show effects can proceed even after the host observes an abort. This is different from the repaired executor check before downstream dispatch. Do not advertise immediate revocation through the effect boundary without adapter-level evidence.
- **Portable locks:** missing/corrupt owner metadata and reused/live PIDs can require operator recovery; backend changes may intentionally block startup. No forced reclaim or lock deletion was performed. Process-death testing does not establish power-loss durability or every stale-reclaim interleaving.
- **PID verification:** matching pong plus persisted PID is stronger than trusting the file, but remains a same-user socket protocol and a check-then-signal operation, not an OS process handle. No hostile same-user socket impersonation/PID-reuse race qualification was supplied.
- **Evidence retention:** temporary JSONL, built-artifact provenance and CI results should be retained with the final qualification packet. Current log hashes preserve the reviewed outputs, not missing original fixture state.

## 5. Completion-event correction: accepted with limits

`tests/fixtures/d9-review-observer.mjs` wraps `EventLog.prototype.append` only in the daemon process loaded with that observer. `coordination status/results` can finalize from another CLI process. The observer therefore cannot serve as a cross-process completion ledger.

`f812ed95` changes the probe to load the run via `CoordinationStore`, read its persisted session through `readRunSessionEvents`, and require exactly one event for that run with the returned aggregate ref/fingerprint. It preserves assertions for completed worker, exact output, single file event, single consumed dispatch approval, no second approval and verified status. It does not change production authorization, substitute a reviewer verdict or turn a CLI label alone into evidence.

The historical corrected probe's tool write is allowed by `owned-path-rule` after dispatch approval. It is **not** an end-to-end demonstration of a separately paused tool grant resumed by the daemon. Resumer qualification comes from the dedicated acceptance/process/SIGKILL evidence, whose limits remain applicable. Sharing the production session reader verifies wiring but is not an independent parser audit; missing historical files and EPERM prevent stronger claims here.
