# src/tracing — Langfuse Tracing Facade (leaf module)

## Purpose

The ALiX-owned tracing boundary. Exposes a single `TraceClient` facade — the only tracing API runtime seams ever see — backed by a Noop client (the default) and a Langfuse SDK adapter. ALiX owns what a trace means; Langfuse owns how it is transported. This module is observational only: it can enrich an execution but can never determine whether the execution succeeds or fails.

> Module status: **module boundary (Task 3), NoopTraceClient (Task 4), capture policy (Task 5), Langfuse adapter (Task 7), parent-run translation (Task 8), runtime client factory (Task 9), run-root wiring (Task 10), provider model-span wiring (Task 11), tool-span wiring (Task 12), bounded flush (Task 13), bounded shutdown (Task 14)** of `docs/superpowers/plans/2026-09-06-langfuse-tracing-implementation-plan.md`. Design contract: `docs/superpowers/specs/2026-09-06-langfuse-tracing-design.md`. Types/interface, inert no-op client, pure capture policy, the Langfuse v3 adapter, adapter-level parent-run translation, the memoized `createTraceClient` selection factory (+ `getProcessTraceClient` deep-seam accessor), the root run lifecycle wired into `processTurn`/`runTaskCore`/`processChat` (Task 10), provider model spans emitted by `withProviderContracts` (Task 11) in `src/providers/`, tool spans emitted by `ToolExecutor.execute` (Task 12) in `src/tools/`, the bounded flush (`endRun` → flush bounded by `flushTimeoutMs`, Task 13), the bounded shutdown (Task 14), the chat continuation run-identity pin (Task 19), the run-level disabled/misconfigured regression guards (Task 20), the bounded-flush edge + tracing-config validation deltas (Task 21), and the static Langfuse-import boundary scan (Task 22) all exist today; config lives in `src/config/` (Task 6).

## Local Contracts

- **Selection is once per process (Task 9):** `client-factory.ts` is the module's only composition entry. Bootstrap seams call `await createTraceClient(resolvedConfig.tracing)` once and receive a `TraceClient`; they never branch on `config.tracing.enabled` afterward. The factory memoizes the first `enabled === true` result (adapter or Noop-after-failure) as a promise for the process lifetime — changing enabled tracing config requires a process restart. A disabled config resolves to the shared frozen `NOOP_TRACE_CLIENT` and imports/constructs nothing.
- **Adapter load is lazy (Task 10 review fix):** `client-factory.ts` must never statically import `langfuse-client.ts`; the adapter (and the `langfuse` SDK it imports) is reached only through the factory's dynamic `import()` on the enabled branch. A default-disabled process that imports the factory — via the run/tui/agent-loop wiring — must not parse or evaluate the Langfuse module graph. The factory contract is async (memoized promise) so the enabled load can stay lazy; the resolved `TraceClient`'s lifecycle methods remain synchronous except `endRun` (Task 13: async because it awaits the bounded flush).
- **Dependency direction:** runtime seams (`src/agent`, `src/run`, `src/providers/provider-contract-validation.ts`, `src/tools/executor.ts`) import only `TraceClient` + types from this module, or obtain an implementation from `createTraceClient`. Deep seams without a `tracing` config (e.g. `withProviderContracts`) obtain the process client via `getProcessTraceClient()` (Task 11) — config-free, lazy-safe, and guaranteed to be the same memoized instance the run roots use. `langfuse-client.ts` is the ONLY file in the repo that may import `langfuse`, and dynamic `import("langfuse")` is allowed nowhere except `client-factory.ts` (which today dynamic-imports the adapter rather than the SDK). Enforced by `tests/tracing/langfuse-boundary.vitest.ts` (Task 22 static scan) plus the Task 20 module-evaluation probes; nothing outside `langfuse-client.ts` imports `langfuse` or any provider SDK, and nothing outside `src/tracing/` imports the adapter. Replacing Langfuse changes only the adapter, dependency, and config — never seams.
- **Leaf consumption of normalized runtime types:** `src/tracing/` may type-import existing ALiX identity/normalized shapes (`ExecutionContext`, `NormalizedMessage`, correlation ids) — type-only; it does not duplicate or re-own them. The existing `runId`/`sessionId`/`workflowId`/`parentRunId`/`invocationId`/`toolCallId`/`executionId` identity model remains authoritative. No second run identity, no second event/telemetry store.
- **Opaque handles:** `TraceRun`/`TraceSpan` are opaque; callers obtain them from `startRun`/`getRun`/`startModelSpan`/`startToolSpan` and pass them back. Langfuse trace/span/generation objects, SDK ids, and SDK types must never escape the adapter. Deep seams resolve a run via `getRun(runId)`; a null result means skip span creation.
- **One run, one trace (design §14):** the ALiX `runId` IS the Langfuse trace id — exactly one trace per runId, and `startRun` is idempotent per runId; `getRun(unknown)` → null; `endRun(unknown/ended)` → no-op; span end on an unknown/ended span → no-op. Lifecycle methods never throw into agent execution. Chat (no native `runId`) synthesizes ONE `run-<uuid8>` per `processChat` invocation and reuses it across continuation/re-prompt provider calls (R3); a physical provider request → exactly one model span, so streaming emits one span spanning the whole stream and never one per chunk (R6 — pinned by the T16/T17 exactly-once tests). Parentage is the next bullet.
- **Parent-run translation (Task 8):** ALiX `parentRunId` is authoritative and in-process-only (R4). Langfuse has no cross-trace parent field (v3.38 SDK: `CreateLangfuseTraceBody` carries no `parentObservationId`/`parentTraceId`; traces group only via session), so the adapter does NOT merge traces or invent identity. When `startRun(input)` has `input.parentRunId` that resolves to an active run in this adapter whose trace is live, and `input.sessionId` is absent, the child trace is emitted under the parent's session (Langfuse's related-traces container) — child keeps its own trace id and spans, and parentage stays recorded as `metadata.alix.parentRunId`. An explicit child `sessionId` always wins; an unknown/ended/cross-process/failed-parent degrades to a standalone child trace, never throwing. Parentage is never inferred from call order.
- **No network I/O from lifecycle methods:** `startRun`/`startModelSpan`/`startToolSpan`/`endSpan` are synchronous and enqueue/update local SDK state only. `endRun` (Task 13) finalizes the run trace synchronously and then awaits a flush bounded by `flushTimeoutMs` — the ONLY awaited transport wait at a run terminal, and it can delay the agent by at most that budget once (design §12). `flush()` is bounded the same way and never rejects into the caller (timeout resolves; reject → `warnOnce` → continue). `shutdown()` (Task 14) is the process teardown partner: idempotent, bounded by the SAME `flushTimeoutMs` (one net wait on the SDK's own `shutdownAsync`, which flushes internally — never `flush()` plus `shutdownAsync()` stacked), fail-open/reject-absorbed/warn-once, and called exactly once from each entry mode's existing "app closing down" choke point (run CLI handler `finally`, TUI `runTui` `finally`, daemon SIGTERM before `exit(0)`). None of these can change an ALiX run's outcome (fail-open: resolve/reject/timeout → continue).
- **Status vocab:** run + span statuses are `success` / `error` / `cancelled`. Timeouts/denials/failures map to `error`; operator cancellation maps to `cancelled` (matches ALiX activity terminal semantics).
- **Security:** capture applies mandatory redaction before truncation; `full` never means unredacted. Redaction is always enabled and cannot be disabled through configuration or the capture surface. The detector is best-effort and non-exhaustive — callers remain responsible for not intentionally supplying sensitive data for capture. No environment-variable credential resolution anywhere in the tracing path — keys use the existing `cred://` store mechanism.
- **Capture levels & `off`:** capture level `"off"` returns `undefined` from every capture function — facade callers treat `undefined` as "field omitted". `"full"` = full value after mandatory redaction (never bypasses redaction); `"truncated"` = redaction then truncation per `CaptureLimits`. All capture functions return copies; caller-owned inputs are never mutated.
- **Capture/redaction wiring (M1/M2):** `capture.messages` gates BOTH model input and model output text — one shared knob, so `messages: "off"` omits both (M1); `capture.toolOutput` + `maxToolOutputChars` (default 2000) govern tool output text only; tool call args, model reasoning, and error text share `maxMessageChars` (default 4000) (M2). Redaction always runs before truncation and cannot be disabled (`"full"` never means unredacted). The detector is regex-based over common secret shapes (`sk-`/`pk-` tokens, `api_key`/`secret`/`token` assignments, `Authorization`/`Bearer`/`Basic`, `cred://` references, PEM blocks) — best-effort and deliberately non-exhaustive; it is NOT an entropy scan. Callers remain responsible for not intentionally supplying sensitive data.
- **TraceClient contract is async where it transports (Tasks 3/9/13/14):** `createTraceClient(config?)` is `Promise<TraceClient>`; `startRun`/`getRun`/`startModelSpan`/`startToolSpan`/`endSpan` are synchronous, enqueue-only operations; `endRun`, `flush`, and `shutdown` are `Promise<void>` and must be `await`ed by callers (the run roots and entry-mode choke points do). The Noop implementation satisfies the identical async contract at zero transport cost.
- **Instrumentation seam locations:** model spans are emitted by `withProviderContracts` in `src/providers/provider-contract-validation.ts` (one per physical request; run resolved via `getProcessTraceClient()` + `getRun(request.context.runId)`); tool spans by `ToolExecutor.execute` in `src/tools/executor.ts` (run resolved via `ToolCallRequest.runId` — R2, so callers without a runId get noop spans); run roots by `runTaskCore` (src/agent/agent-loop.ts), `processTurn`, and the `processChat` wrapper (src/agent/session.ts). All emit through the same memoized process `TraceClient`.
- **Fail-open everywhere (design §11):** invalid config (empty/non-http(s) `baseUrl`, leftover unresolved `cred://` ref, SDK ctor or adapter module-load throw) → factory `warnOnce` → frozen `NOOP_TRACE_CLIENT`; flush/shutdown rejects and timeouts are absorbed (`warnOnce`, distinct keys) and resolve — tracing can never crash, hang, delay beyond budget, or change the outcome of an ALiX run. Disabled config resolves to the frozen Noop singleton with zero SDK import/construction, zero credential resolution, zero network.
- **Bounded flush/shutdown (T13/T14):** `flush()` and `endRun()` await `withTimeout(sdk.flushAsync(), flushTimeoutMs)` (default 2000 ms); a flush timeout resolves `undefined` ("stop awaiting, continue"); a non-positive/non-finite budget resolves immediately (with-timeout.ts guard — defense-in-depth, the config validator already rejects those). `shutdown()` is idempotent and applies exactly ONE net `withTimeout(sdk.shutdownAsync(), flushTimeoutMs)`: `shutdownAsync` is itself a final internal flush, so no separate flush budget is stacked on top.
- **Tracing config (Task 6/T21):** the single source of truth is `src/config/` — `TracingConfig` in schema.ts, defaults + per-field deep-merge arm in defaults.ts/loader.ts; `src/tracing/` type-imports it only. `enabled` defaults `false`; `langfuse.baseUrl` defaults `""` and must be a valid `http(s)` URL when enabled; `langfuse.publicKey`/`secretKey` default to the fixed store references `cred://langfuse/publicKey` / `cred://langfuse/secretKey` and resolve store-only (never env vars); capture levels/limits and `flushTimeoutMs` (positive integer) as laid out in `docs/configuration.md#tracing`. Do not expose SDK tuning knobs (e.g. `debug`, `flushIntervalMs`) without a concrete ALiX requirement (design §9).
